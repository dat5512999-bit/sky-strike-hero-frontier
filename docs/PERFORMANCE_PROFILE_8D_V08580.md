日期：2026-09-29。針對「少量敵人仍卡頓」；不新增士兵、不修改軍團傷害或平衡。本輪以 PM 定義問題、架構定位資料熱路徑、UX 拆分量測、開發小範圍修正、QA 對照、文件與版本同步的順序處理。

## D1–D2：問題與可核對證據

使用者截圖：11 怪、×2、6 FPS、影格 P95 299.8 ms、更新 P95 157.7 ms、繪圖呼叫 P95 1.9 ms。不能再預設是繪圖瓶頸；繪圖呼叫耗時也不等於 GPU 完成時間。

舊戰鬥 benchmark 只涵蓋部分模擬，沒有完整 DOM／ProfileStore／實際存檔，因此不能用來排除主執行緒問題。v0.85.79 所謂排序陣列「根因」降級為未量化的改善假設。

## D3–D4：隔離與根因驗證

在獨立 `127.0.0.1:4174` 載入真實 td.html、100 張建造卡、29 張傭兵卡，選矮人英雄及軍團；存檔替換為記憶體儲存，加上 0／256 KiB／1 MiB 合成字串。每組執行完整 `updateUi()` 20 次。

```text
每 100 ms HUD 更新
  → 100 張建造卡說明／過濾 + 29 張傭兵權限
  → FrontierApp.isAdmin()
  → ProfileStore.current()
  → JSON.stringify / parse 整份角色資料（每個 HUD 約 229 次）
```

同一瀏覽器 A/B 實測（毫秒；P95 按排序後 floor((N−1)×.95) 取樣）：

| 合成額外資料 | 修正前中位數 / P95 | 修正後中位數 / P95 | 修正後 20 次 HUD 的 current() 次數 |
| --- | --- | --- | --- |
| 0 | 2.8 / 3.4 | 1.7 / 2.8 | 0 |
| 256 KiB | 42.4 / 52.5 | 1.6 / 1.9 | 0 |
| 1 MiB | 270.2 / 275.6 | 1.5 / 1.9 | 0 |

修正前前兩組各記錄 4,580 次複製；1 MiB 組記錄 4,809 次（其中額外一次 HUD 由圖片完成事件觸發）。存檔大小是實驗控制值，**不是讀取使用者真實存檔所得**。這確認一條可重現的卡頓原因，不宣稱已證明使用者那一幀的唯一原因。

## D5：永久修正與架構

- `ProfileStore.isAdmin()` 只讀取當前 kind，`allows()` 只讀身份與 unlocks 並回傳布林，不複製存檔、不暴露可變物件。
- `FrontierApp.isAdmin()` 改走新查詢；不缓存身份，因此切換、匯入與回復輪次立即反映。
- `current()` 保留深複製；`change()`／原子 persist／多分頁衝突保護未修改。沒有資料庫、HTTP API 或資料 schema 變更。
- `TDGame` 啟用監視器時才計時 HUD；每幀清零，`simulationMs = updateMs - uiMs`。UI P95 是 120 幀窗口內（含未更新 HUD 的零值）統計，不等於只看 HUD 呼叫的微基準。
- 不降低模擬頻率、倍速、怪物數或技能效果，所有軍團共用修正。
