# 南方視覺一致與效能 8D（v0.85.79）

> **2026-09-29 更正：** 下文把排序陣列配置判為卡頓根因，證據不足；限制頻率也不能排除小地圖或版面成本。使用者後續截圖為 11 怪、6 FPS、更新 P95 157.7 ms。v0.85.80 在完整 HUD 重現「權限查詢反覆複製玩家存檔」造成數百毫秒更新，詳見 [後續 8D 與前後對照](PERFORMANCE_PROFILE_8D_V08580.md)。本文件保留歷史修正紀錄，不作為卡頓已結案的證據。

日期：2026-09-29。範圍只包含埃及島英雄選角、矮人塔的戰場呈現，以及使用者回報的戰鬥卡頓；不新增埃及軍團或改寫劇情。

## D0–D2：問題、團隊與量測方式

- **D0｜啟動原因：** 戰場中的埃及英雄為男性，但選角為女性；選角技能圖未可靠顯示；矮人支援塔可部署卻畫成通用方塊／青色圓點；實戰出現卡頓。
- **D1｜責任分工：** PM 確認「看得到且與戰場一致」為驗收標準；美術與 UI 處理肖像、圖示與塔剪影；系統模組處理每幀與每子步配置；QA 建立回歸。
- **D2｜復現與證據：** 檢查 `TDGame.updateMonsterConvoy`，發現每個模擬子步都使用 `filter().sort()` 建立新怪物陣列；在低幀率或 ×3 加速時可一幀執行多個子步，放大垃圾回收與排序尖峰。小地圖已在 `MiniMapView` 限制為每 100ms 一次，排除為此次主因。選取單位時的定位會反覆呼叫 `getBoundingClientRect()`，亦可能造成不必要版面量測。

## D3–D5：圍堵、根因與修正

- **D3｜立即圍堵：** 保留既有的模擬追趕上限與 ×3 自動降速保護；不偷偷丟棄傷害、敵人或波次。
- **D4｜根因：** 車隊排序陣列在每一子步新配置；選取面板在連續繪圖中重複量測版面。視覺端另有塔專用畫筆只掛在可被後續美術模組包裝的原型鏈，沒有獨立後援。
- **D5｜永久修正：** `Performance8DOptimizer` 重用 `convoyOrder`，保留原本的排序、間距與更新順序；選取面板量測上限為 20Hz。`ImperialFactionArt` 將四座矮人塔拆成塔弩、符文熔爐、迫擊堡與雙砲堡壘；`Building` 在通用畫筆失敗時直接呼叫此繪製器。選角技能採 DOM 圖示而非可被裁切的偽元素。

## D6：驗證

執行 `npm run test:southern`：

- 埃及肖像固定為 `hero-selection-v2.png`，技能容器包含三個 `hero-skill-icon`。
- 矮人四塔均完成獨立 Canvas 繪製且 Canvas 狀態平衡。
- 車隊連續兩次更新重用同一排序緩衝區，所有怪物仍各更新一次；來源不得回到 `this.monsters.filter(...)` 的配置模式。
- 既有南方英雄 8D 技能安全／平衡回歸仍包含在同一指令。

## D7–D8：防再發與結案判準

- **D7：** 新增 `tests/td-visual-performance-8d.test.js`，將肖像版本、DOM 圖示、塔繪製與排序緩衝列為自動驗收；Service Worker 必須快取新圖與兩個修正模組。
- **D8：** 完成標準是刷新到 `sky-strike-v0.85.79` 後，埃及選角與戰場皆為男性、三項技能看得見、放置四種矮人塔皆非通用方塊；效能監視器的更新 P95 在大量怪物或 ×3 時不再因車隊陣列配置產生同類尖峰。若仍卡頓，請在遊戲選單開啟「效能資訊」並提供當時的 FPS、更新 P95、繪圖 P95、怪物數與倍速，下一輪會以該數據處理繪圖瓶頸。
