# Battlefield / Camera / Canvas Audit（2026-09-14，分析，不改遊戲程式）

本文件同時對照玩家提供的 1280×720 戰鬥介面概念圖。概念圖是視覺與 UX 方向，不是可直接複製的版面或素材。此次沒有修改 Canvas、地圖、路徑、數值或輸入座標。

## 現況與耦合

- `td.html` 的戰鬥 Canvas 固定 720×720；`src/td/config.js` 的 `width`／`height` 也都是 720，並有 14 個固定路徑點，首尾延伸到畫面外。這是**世界座標**，不是單純圖片解析度。
- `TDGame.canvasPoint()` 使用 Canvas 畫面矩形反算 720 座標；`TDGame.draw()` 直接以同一座標繪製背景、角色、塔、怪、投射物、回饋。沒有 Camera 物件、平移或縮放矩陣。
- `Monster.update()` 沿 `config.path` 移動；怪物的 `visualPosition()` 只為三個小幅錯位與轉彎平滑服務。`Projectile` 的追蹤、Splash、Chain、`Hero`／`Building`／`CombatUnit` 的索敵仍使用怪物邏輯 `x/y`，僅部分線段、跳字、Hover 使用視覺座標。
- `BuildSystem.canPlaceAt()` 有 42／678、62／674 邊界與距路徑 55 的硬值；`NavigationSystem` 依 `config.width/height` 建格，另有頂端 48、邊緣 24 等界線；`HeroRoster` 暗影閃擊仍有 695 硬值。改世界尺寸或路徑並非只改一個設定。
- `ArtSystem.drawBackground()` 將單張背景圖畫滿整個 720 世界；英雄約 112 世界單位高、塔約 106–118、守軍約 92–114、怪物依種類約 58–108。角色相對道路與部署區確實偏大，這是世界內比例，不是 CSS 卡片大小。
- 桌面 CSS 的戰場**容器**可佔很大寬度，但 Canvas 依高度保持正方形，旁邊寬度用同一背景圖裝飾；那不是可部署、可戰鬥的擴充地圖。以 1920×1080 為例，當前 42px 上欄、48px 波次列、約 300–350px 右欄後，可顯示的正方形 Canvas 高度約 960–970px，真正戰場像素面積約全視窗 45%，雖然戰場容器約 70% 以上。這是 CSS 推算，不是實際像素量測。
- 手機橫式 `LayoutSystem` 以寬、高與 coarse pointer 判斷，手動可強制切換。CSS 仍用方形 Canvas、右指揮欄與底部 Drawer；高度很矮時 Canvas 會比左戰場容器窄。手機直式另有後備排列，但戰鬥邏輯共用。

## 與概念圖的差距與風險分級

等級 A：純 UI／CSS／Presentation 低風險；B：Layout／Rendering／Input 中風險；C：世界座標／路徑／相機／地圖高風險。A 不表示不用目視驗收。

| --- | --- | --- | --- |

## 可行路線，不是本輪實作清單

| 方案 | 能改善什麼 | 無法解決什麼 | 判斷 |
| --- | --- | --- | --- |
| A. 只整理 HUD／Drawer／右欄 | 戰場「看起來」更像主角，操作容易找 | 正方 Canvas 仍受高度限制，裝飾區仍不能玩 | 可先做，不浪費，但不能宣稱完成大戰場 |
| B. 720 世界內加鏡頭縮放／平移 | 局部角色比例、聚焦可調 | 縮小看全圖會讓角色更小；放大會裁進出口與建造區 | 須先做可關閉原型，驗證輸入反算與視野 |
| C. 改成寬邏輯世界／重新構圖 | 真正加寬可部署地形和戰略位置 | 牽動圖資、Path、導航、建造、技能範圍、平衡 | 高風險，必須獨立里程碑與回退方案 |
| D. 混合：先整理 UI，再設計寬地圖＋受控鏡頭 | 最有機會接近概念圖的戰場主導感 | 工時、圖資、真機性能與平衡驗證成本最高 | 未來 80–90% 方向；先小原型再決策 |

## 九個直接結論

1. **不改 720×720 能否約 70% 接近？** 若指資訊層級、邊緣操作與美術語氣，大約可接近「感受上的多數」；若指圖中寬廣且可玩的戰場面積，不能。約 70% 不是實測分數，不應當作交付指標。
2. **80–90% 最可能要改什麼？** 寬邏輯世界或有明確視野規則的鏡頭、重構地圖構圖與路徑、建造區、點擊座標反算、單位比例與密集戰效能；非單一 CSS 改動。
3. **現在可做且不浪費？** 貼邊薄 HUD、卡片視覺層級、低頻資訊折疊、技能／資源可讀性、有限特效節制，以及保留單一 UI 資料來源。此次已完成的 Drawer 分類、角色技能資料與 PC／手機共用邏輯可沿用。
4. **等 Audit 後？** 本 Audit 已完成靜態程式分析；下一步應先做可撤回的 B／D 小原型，再決定 Camera、世界尺寸、地圖與單位 Scale，不能直接進正式地圖重做。
5. **右側 Panel 保留嗎？** 保留「功能」，未必保留現在的整塊常駐外形。PC 可收成窄英雄／選取欄，詳情按需展開；手機不能照搬 PC 右欄，仍共用底層資料。
6. **Drawer 可變薄快捷列嗎？** 可以，先讓常用卡與分類顯眼、詳細資訊第二層；若窄到名字／定位／成本不可辨，反而降低決策品質。正式改版需 PC 與手機橫式視覺原型。
7. **PC／Mobile 共用邏輯只換 Presentation？** 可以且現有架構已大致如此：同一 `TDGame`、`BuildSystem`、建造卡與戰鬥資料，`LayoutSystem`／CSS 切呈現。Input 仍須針對觸控命中尺寸驗證。
8. **角色相對地圖過大嗎？** 是，有此視覺趨勢：英雄約佔畫布高度 15.6%，塔／兵也約 13–16%，使地圖像小型棋盤；但直接全體縮小會影響辨識與點選。先以顯示比例與 hit area 分離原型驗證。
9. **該單純放背景、改 World、加 Camera、改 Scale，還是混合？** 混合。先減少 UI 遮擋；再原型評估寬世界／鏡頭；最後按新地圖調整單位顯示比例。單純擴背景只是裝飾，不會新增戰略空間。

## 結論與停點

- **短期可以先做：** HUD 與側欄資訊瘦身、建造卡與技能列可讀性、效能量測基線、真機橫式 Drawer 驗收。這些都不需要改戰鬥數值。
- **等本 Audit 後再做：** 可關閉的鏡頭／寬地圖小原型；對照 1920×1080、筆電、手機橫式，量測可玩像素比例、輸入誤差、路徑可見度與 30 怪幀率，經玩家確認才擴大。
- **目前不建議：** 只拉伸背景宣稱擴圖、對整個 UI 做 `transform: scale`、立即改 `config.width/height`、裁切進出口、硬塞 Minimap、另外建立手機 Gameplay、照抄概念圖素材。
- **STOP：** 這份 Audit 不授權 P5；本輪到此為止，等待人工決定原型方向。
