## 問題與產品判斷

玩家在第四章「潮門外流」第 3/5 幕「本關目標」看到純深色底，誤以為沒有配圖。線上 `chapter4-tidegate-readings-v1.png` 與賽洛肖像均回應 HTTP 200，檔案大小及 SHA-256 與本機一致；在全新 Edge 工作階段，目標圖片約 15.2 秒才完成載入。原介面在等待圖片時沒有備用畫面或狀態，因此造成空白觀感。這不是劇情資料指錯檔案，不能只把同一張圖再上傳一次。

## 設計與實作

`FrontierApp` 的故事卡以「關卡地圖（或已成功載入的上一幕）」作為底圖；目前幕圖片載入完成才淡入覆蓋。等待時顯示「畫面載入中…」；真正載入失敗時保留底圖、顯示可理解的錯誤與「重新載入畫面」，重試加查詢參數避開可能失效的快取。當前圖成功後才預載下一幕，避免與當前大圖搶頻寬。換幕時忽略已移除舊節點的載入回呼。音樂開關只更新自身，不再重繪整張卡及取消圖片下載。

實作位於 `src/td/app/FrontierApp.js` 與 `td-lobby.css`；`scripts/verify-pages-release.cjs` 另外比對 11 張新增故事圖和此關賽洛肖像，防止未來「程式上線但素材漏傳」的假陽性。維持既有 86 幕圖片、橫向佈局、敘事文字與音樂；沒有新資料庫、HTTP API、權限、存檔欄位或執行依賴。首次下載大圖仍取決於網速；這次修復的是等待期間的空白與失敗處理，不宣稱已降低 PNG 的傳輸大小。

## QA、發布與回復

`tests/td-story-art-loading.test.js` 檢查底圖／提示、成功載入與下一幕預載、舊回呼、失敗重試及線上驗證檔案清單。瀏覽器以人為延遲圖片 4–5 秒測得等待期間有地圖與提示、原圖完成後切為 `ready`；模擬首次 HTTP 503，重試後圖片正常顯示；音樂開關期間同一 `<img>` 不被替換且只有一次圖片請求。線上素材 12 筆亦經唯讀比對正確。完整回歸另執行 `npm test`、`npm run check` 與 `git diff --check`；發布後須以實際 GitHub Pages 和手機慢網重新驗證。

本機完整回歸結果：`npm test` **1025/1025**、`npm run check` 與 `git diff --check` 通過。當前工作樹另有尚未完成的冒險模組修改，因此線上整版驗證不能把本機未提交入口直接與現有 Pages 相比；上述 12 張線上圖片另以唯讀位元組比對，均正確。

本項修補規格版號 **v1.0.0**，目前在本機工作樹。正式發布要在沒有混入其他未完成工作的版本中同步提交程式、樣式、測試、文件，並提升應用版號與 Worker 快取鍵；再核對線上實際畫面，而非僅看 HTTP 200。更新前保留前一完整 Git 提交與玩家 JSON 備份；如有回歸，成套回退程式、樣式、版號及 Worker，不刪玩家資料。
